# ClawGuard 登录注册与邀请码系统实现说明

## 1. 当前管理员权限是什么

当前系统已经支持 `admin` 与 `user` 两种角色，角色信息保存在数据库 `User.role` 字段中。

现阶段，`admin` 账号和普通用户的区别主要有两层：

### 1.1 数据层区别

- `admin` 用户在数据库中 `role = admin`
- 普通用户在数据库中 `role = user`

这意味着系统已经具备“区分管理员与普通用户”的基础能力，后续如果要扩展管理员页面、管理员专属接口、审计能力，都可以直接沿着这个字段继续做。

### 1.2 当前实际生效的区别

当前版本里，`admin` 的主要管理能力**不是通过前端页面实现**，而是通过服务器脚本实现：

- 创建管理员账号
- 创建邀请码
- 查看邀请码列表
- 修改邀请码
- 禁用邀请码
- 查看邀请码使用记录

也就是说：

- 普通用户：只能通过前端注册、登录、使用普通业务功能
- 管理员：当前通过服务器端脚本完成邀请码管理

## 2. admin 账号和普通用户现在有什么不同

### 当前已经不同的地方

- `admin` 登录后返回的用户对象中，角色为 `admin`
- 后端签发的 token 中会携带 `role`
- 前端会拿到当前用户角色
- 后续可以基于这个角色继续扩展管理员专属页面或接口

### 当前还没有专门做出的区别

这点很重要，需要说明清楚：

当前版本**没有单独做管理员前端后台页面**，也没有单独做“只有 admin 才能调用的前端按钮入口”。

因此目前：

- `admin` 和普通用户在前端主界面上差异不大
- 主要差别体现在数据库角色字段与服务器侧管理操作方式

换句话说，当前管理员能力是：

**角色已经建好，实际管理操作通过后端脚本完成，而不是通过网页控制台完成。**

这是一种有意选择的 MVP 方案，适合当前比赛阶段：

- 先把核心认证和邀请码闭环做扎实
- 不额外投入成本做后台管理 UI

## 3. 这次一共做了哪些修改

本次改造的目标，是把原本前端演示级的“假登录/假注册”升级为：

- 后端真实认证
- 数据库驱动的用户体系
- 数据库驱动的邀请码体系
- 服务器脚本管理的邀请码能力

整体上主要改了四部分：

1. 数据库结构
2. 后端认证与邀请码逻辑
3. 前端登录注册逻辑
4. 运维与管理脚本

## 4. 数据库层做了什么

本次新增了 3 张核心表：

### 4.1 User

用于存储真实用户账号。

主要字段：

- `username`
- `passwordHash`
- `phone`
- `role`
- `status`
- `createdAt`
- `updatedAt`

作用：

- 替代原来前端 `localStorage` 里的假用户库
- 支持区分 `admin` 与 `user`
- 密码改为后端哈希存储，而不是明文

### 4.2 InviteCode

用于存储邀请码本体。

主要字段：

- `code`
- `maxUses`
- `usedCount`
- `expiresAt`
- `status`
- `note`
- `createdBy`

作用：

- 支持随机生成邀请码
- 支持设置可使用次数
- 支持设置有效期
- 支持禁用邀请码

### 4.3 InviteUsage

用于记录邀请码被谁使用。

主要字段：

- `inviteCodeId`
- `userId`
- `usedAt`

作用：

- 记录具体哪个用户使用了哪个邀请码
- 方便审计和比赛展示

## 5. 后端做了什么

### 5.1 新增认证基础工具

新增文件：

- `web/server/lib/auth.mjs`

负责：

- 用户名、手机号标准化
- 密码校验
- 密码哈希
- 密码比对
- token 签发
- token 校验
- 从请求里提取 Bearer token

### 5.2 新增认证服务

新增文件：

- `web/server/services/authService.mjs`

负责：

- 用户注册
- 用户登录
- 获取当前登录用户

注册时会执行：

1. 校验用户名、密码、手机号
2. 校验邀请码是否存在、是否可用
3. 创建用户
4. 增加邀请码使用次数
5. 写入邀请码使用记录
6. 返回 token 和用户信息

### 5.3 新增邀请码服务

新增文件：

- `web/server/services/inviteService.mjs`

负责：

- 创建邀请码
- 查询邀请码
- 修改邀请码
- 禁用邀请码
- 校验邀请码是否可注册
- 查询邀请码使用记录

### 5.4 新增认证 API

后端新增接口：

- `POST /api/auth/register`
- `POST /api/auth/login`
- `POST /api/auth/logout`
- `GET /api/auth/me`

含义：

- 注册用户
- 登录用户
- 退出登录
- 获取当前登录用户

### 5.5 调整受保护接口

动态沙箱检测相关接口不再只依赖一个前端传入的状态字符串，而是开始读取真实登录 token。

这意味着：

- 未登录时，后端会拒绝访问
- 登录后，前端带 token 请求，后端才允许通过

## 6. 前端做了什么

### 6.1 核心认证逻辑从假登录改成真登录

修改文件：

- `web/src/hooks/useAuth.js`

原来：

- 用户数据保存在浏览器本地
- 登录时在前端直接比对账号密码
- 注册时在前端直接写入 `localStorage`
- 邀请码在前端写死常量校验

现在：

- 登录调用 `/api/auth/login`
- 注册调用 `/api/auth/register`
- 刷新时调用 `/api/auth/me`
- 退出调用 `/api/auth/logout`

### 6.2 新增前端会话管理

新增文件：

- `web/src/lib/authSession.js`

作用：

- 在前端 `sessionStorage` 存储 token 和用户信息
- 生成带 `Authorization` 的请求头

### 6.3 登录注册弹窗改成异步真实请求

修改文件：

- `web/src/App.jsx`
- `web/src/features/openclaw-exposure/components/ExposureDetailTable.jsx`
- `web/src/features/openclaw-governance/pages/OpenclawGovernancePage.jsx`

改动内容：

- 登录/注册从同步假逻辑改成异步请求后端
- 增加提交中状态
- 登录注册失败时展示后端返回的真实错误信息

### 6.4 移除前端写死邀请码

修改文件：

- `web/src/config.js`

原先前端有固定邀请码常量，现在已去掉。

当前邀请码完全以后端数据库为准。

### 6.5 本地开发代理补充认证接口

修改文件：

- `web/vite.config.js`

补充了开发时的 `/api/auth` 代理配置，以及相关受保护接口代理。

作用：

- 前端开发环境能把认证请求转发到后端

## 7. 管理功能是怎么实现的

本次没有做管理员后台页面，而是采用**服务器后端脚本管理**。

### 已新增的管理脚本

- `web/server/scripts/create-admin.mjs`
- `web/server/scripts/create-invite.mjs`
- `web/server/scripts/list-invites.mjs`
- `web/server/scripts/update-invite.mjs`
- `web/server/scripts/disable-invite.mjs`
- `web/server/scripts/show-invite-usage.mjs`

### 管理脚本分别负责什么

`create-admin.mjs`

- 创建管理员账号
- 更新管理员密码、手机号、状态

`create-invite.mjs`

- 创建邀请码
- 可设置次数、有效期、备注

`list-invites.mjs`

- 查看邀请码列表
- 查看剩余使用情况

`update-invite.mjs`

- 修改邀请码最大次数
- 修改过期时间
- 修改备注
- 调整状态

`disable-invite.mjs`

- 直接禁用某个邀请码

`show-invite-usage.mjs`

- 查看某个邀请码被哪些用户使用

## 8. 当前系统完整流程是什么

### 用户注册流程

1. 用户打开前端注册弹窗
2. 输入用户名、密码、手机号、邀请码
3. 前端调用 `/api/auth/register`
4. 后端校验字段与邀请码
5. 后端创建用户
6. 后端消耗邀请码
7. 后端写入使用记录
8. 后端返回 token 和用户信息
9. 前端保存登录态并进入已登录状态

### 用户登录流程

1. 用户输入用户名和密码
2. 前端调用 `/api/auth/login`
3. 后端查数据库
4. 校验密码哈希
5. 返回 token 和用户信息
6. 前端存储 token

### 管理员管理邀请码流程

1. 管理员或运维人员登录服务器
2. 执行管理脚本
3. 脚本调用后端服务逻辑
4. 服务逻辑更新数据库
5. 前端注册流程自动使用新的邀请码规则

## 9. 当前方案的特点

### 优点

- 登录注册已经是真实后端认证
- 邀请码已经是数据库驱动，不再是前端写死
- 管理能力已经具备，不依赖临时手工改数据库
- 支持邀请码次数限制、有效期、禁用、审计
- 非常适合当前比赛阶段的 MVP

### 当前有意没有做的部分

- 没有单独的管理员管理页面
- 没有做评委专用邀请码类型
- 没有做更细的 RBAC 权限系统

这并不是缺陷，而是当前阶段的范围控制：

- 先完成核心认证闭环
- 管理端先用服务器脚本
- 后续如需产品化，再补后台页面与更复杂权限

## 10. 现在可以怎么向别人解释

可以这样描述当前实现：

“我们把原本前端演示级的登录注册，升级成了后端真实认证体系。用户信息、邀请码、邀请码使用记录都已进入数据库。注册时必须通过邀请码，后端会校验邀请码是否存在、是否过期、是否超出次数，并在注册成功后自动扣减使用次数并记录使用行为。当前管理员能力采用服务器脚本方式实现，可完成邀请码创建、查看、修改、禁用与使用记录审计。这样既保证了系统完整性，也控制了比赛阶段的实现成本。” 

## 11. 当前最重要的事实总结

- `admin` 角色已经真正进入数据库和 token
- `admin` 与 `user` 已在数据层区分
- 当前管理员管理能力主要通过服务器脚本实现
- 前端登录注册已经切换到真实后端接口
- 邀请码系统已经从前端写死变成数据库驱动
- 注册、登录、邀请码校验、邀请码消耗、使用记录都已经打通
